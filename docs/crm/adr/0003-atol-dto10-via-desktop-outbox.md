# ADR-0003: Фискализация через АТОЛ ДТО10 из десктопа с устойчивой очередью

- **Статус:** принято
- **Дата:** 2026-09-27

## Контекст

ККМ АТОЛ подключается к компьютеру кассира. Драйвер ДТО10 поднимает локальный
веб-сервер (`http://localhost:16732/api/v2/requests`), который принимает
JSON-задания и выполняет их асинхронно (статусы `wait → inProgress → ready`,
а также `error`, `blocked` и другие). Сбой между «чек напечатан» и «результат
записан» не должен приводить ни к потерянному, ни к двойному чеку.

## Решение

- С ДТО10 работает Rust-часть десктопа (Tauri), а не webview: нет проблем с
  CORS, код тестируется.
- Логика вынесена в крейт `buzz-atol` без зависимости от Tauri: wire-типы,
  клиент, опрос статуса, SQLite-очередь (outbox) и драйвер состояний.
- Продажа сначала проводится в relay (проверка остатка до приёма денег), затем
  фискализируется. UUID задания детерминирован: `UUIDv5("sell:" + doc_id)`.
- Строка очереди удаляется только после записи события фискального чека
  (`42120`) в relay. Неоднозначные состояния (`blocked`, пропавший результат)
  не повторяются автоматически, а переходят в `needs_attention` и ждут решения
  человека.
- Для тестов и ручной проверки есть эмулятор веб-сервера ДТО10
  (`buzz-atol-emulator`).

## Альтернативы

- **АТОЛ Онлайн (облако)** — не нужна физическая ККМ, но требуется договор;
  может стать вторым адаптером позже.
- **Запросы из webview** — зависят от CORS-заголовков ДТО10 и хуже
  тестируются.

## Последствия

- Нет офлайн-кассы: фискализация ждёт, пока relay примет продажу.
- Имена ставок НДС 22% (`vat22`, `vat122`), единицы измерения ФФД 1.2 и ответ
  на повторный UUID нужно один раз сверить на реальном устройстве и закрепить
  golden-фикстурами.
